conflict-detect | Implement conflict detection as lib/plan.sh, per SPEC.md section 3.1. One headless call on PLANNER_MODEL (config key, falls back to the CLI default) is given the parsed task list and the SOURCE_GLOBS file inventory, and must return machine-parseable JSON mapping each task to its likely files plus a collision report of overlapping pairs, which is written to the run dir as plan.json. Parse and generate JSON with small node one-liners only — no jq, per CLAUDE.md. Sort every task into exactly one of three buckets: DISJOINT, COLLIDING-SPLITTABLE, INHERENTLY-COUPLED. A malformed or unparseable model response is a hard failure naming what was wrong, never a guess or a silent fallback to "everything is disjoint" — that would be the most dangerous possible failure, since it would green-light a colliding fan-out. Add SOURCE_GLOBS to lib/config.sh with its documented default. The agent is mocked via CLAUDE_BIN in tests, so add a shim mode that returns a canned plan; ship tests covering a clean disjoint plan, a detected collision, and a malformed response.
plan-cmd | Replace the placeholder `plan` subcommand with the real dry run described in SPEC.md section 2, and remove the corresponding entry from SPEC.md section 9. It runs conflict detection via lib/plan.sh and prints the three buckets with the file overlaps that produced them, touching nothing — no worktree, no branch, no run dir mutation beyond plan.json. It is the command a human runs before committing to a fan-out. Ship with tests, including one asserting it creates no worktrees and no branches.
refactor-gate | Implement the gated refactor stage per SPEC.md section 3.2 — the one human checkpoint in the whole pipeline, so it must be conservative. For each COLLIDING-SPLITTABLE group, generate a refactor PLAN ONLY: which files split, into what, what moves where, and why that makes the colliding tasks disjoint. Print it and STOP for stdin approval (approve / reject / edit); default to reject on empty input or EOF, exactly as the base-branch confirmation in seed.sh does. Only on approval execute it: behavior-preserving changes only, run the full suite afterwards, commit only on green, and never weaken or edit an existing test to make it pass. A red suite means revert and report. Never fan out on a red baseline. Ship with tests covering approve, reject, EOF-defaults-to-reject, and the red-suite revert path.
lane-check | Implement lane-violation warnings per SPEC.md section 2. At gate time, diff the files the agent actually touched against the files plan.json predicted for that task. Straying outside the predicted lane writes a warnings/<task> record — the seam lib/report.sh already reads to render PASSED-WITH-WARNING — and must NEVER fail the task; this is warn-only, and making it blocking is an explicitly deferred decision (SPEC.md section 7). A task with no plan.json prediction (a run-one, say) is not a violation and must not warn. Ship with tests covering an in-lane task, a straying task, and a task with no prediction.
coupled-serial | Make the INHERENTLY-COUPLED bucket run sequentially, each task rebased on the previous one's result, per SPEC.md section 3.1. This is the one place tasks must NOT be parallel: they touch the same logic by definition. Extend the fan-out scheduler so a coupled group is dispatched in order, with each task cut from the previous task's branch rather than from BASE_BRANCH, and abandon the rest of a group when one of its tasks fails — a task rebased on a failure is meaningless. Tasks left undispatched that way are SKIPPED, which is exactly what that state exists for. Ship with tests proving the ordering, the rebasing, and that a mid-group failure skips the remainder rather than running it.
